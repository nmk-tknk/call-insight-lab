# 情報量の棚卸し: スキーマ v0.3 で何が落ちるか

- 作成日: 2026-09-16
- 対象: `poc/schema/v0_3.sql`
- 問い: このスキーマで情報量が落ちない保証はあるか

## 0. 結論

**保証はない。構造化は定義上、情報を落とす。** ただし v0.3 は次の 2 つの性質を持つので、損失は「消える」のではなく「まだ集計できない」に留められる。

1. **保存層は無損失(書き起こしの範囲で)。** `turns.text` に発話を逐語で保持し、注釈はすべてスタンドオフで別表に置く。注釈層が何を落としても、原文は残る。
2. **追加は既存表を変えずにできる。** 落ちている情報は、新しい表または列を足し、新しい `annotation_run` で埋め直せば回復する。ただし §2 の「取り込み時にしか得られない情報」だけは、後から再注釈しても戻らない。

したがって問うべきは「落ちるか」ではなく、(a) **取り込み時に必ず保存すべき情報を漏らしていないか**、(b) **分析目的に効く情報のうち、いま注釈層にないものは何か**、の 2 点である。以下で網羅的に棚卸しする。

凡例: 区分 = ◎ 保持 / ○ 部分的に保持 / × 注釈層にない。 回復 = 再注釈(原文から作り直せる)/ 取込時のみ(後から戻らない)/ 除外(意図的に対象外)。 影響 = 目的 (a) 入電増の真因、(b) わかりづらいパターン、(c) それ以外の一般的な VOC・運用分析。

## 7. 推奨: v0.3.1 で追加するもの

**取込時にしか得られないもの(後から戻らないので今決める)**

- `calls`: `direction`, `queue`, `ivr_path`, `wait_sec`, `external_case_id`, `disposition_code`, `audio_uri`(任意)
- `turns`: `asr_confidence`(ターン平均)、任意で `asr_word_confidence`(JSON)
- `events`: `agent_id`(転送後の担当)

**分析目的に直接効くもの(既存表を変えずに追加)**

- `issues.motive_code`(C4)、`issues.confusion_resolved`(C10)、`issues.customer_accepted`(C7)
- `issue_action` に `suggest` を追加(C8)
- `agent_actions(run_id, call_id, issue_idx, action_code)`(C6)
- `turn_flags(run_id, call_id, turn_idx, flag_code)`(X1〜X6)

**保留(要件が出たら追加。既存表は変わらない)**

- `issue_relations`(T5)、`turn_sentiment`(X7)、`mentions`(C14)、`turn_behaviors`(X8)、対象のインスタンス化(C16)

## 8. 与えられる保証の正確な言い方

- 「情報が落ちない」保証はできない。
- 言えるのは、(1) 書き起こしの範囲で原文は無損失に残る、(2) 注釈層のすべての事実は原文の位置を指す、(3) 注釈層にない情報は新しい表と run で後から追加でき、既存の集計は壊れない、(4) 取込時にしか得られない情報は §7 の列を取込設計に含めれば失われない、の 4 点である。
- 残る本質的な損失は、**閉じた語彙に潰す時点で消えるニュアンス**(C2, C11)であり、これは構造化の目的そのものと表裏一体である。原文と根拠引用へのドリルダウンで補う設計になっている。
