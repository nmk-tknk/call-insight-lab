## 1. 結論

**作る価値はある。作るものは「汎用の分析器」ではなく「同じ定義・同じ手順・同じ根拠で数字が出る基盤」である。**

- 通話を LLM で構造化し、その上を単純集計で分析するアプローチは成立する。研究・商用製品の双方がこの方向に収斂している。
- ただし成立条件は、(1) 分析列をすべて閉じた語彙(タグ)にすること、(2) 分析単位を通話ではなく「用件(issue)」にすること、(3) 語彙を自動で育てる仕組みを持つこと、(4) 集計結果を根拠付きで検証できること、の 4 つ。
- 現状の課題「LLM で誰でもそれっぽい分析が出せてしまい、歪んだ結果を信じ込む」に対する解は、抽出精度の向上ではなく、**定義・手順・根拠の強制**にある。v0.3 はそのための設計である。

## 2. コンセプト: 5 つの原則

### 原則 1: 項目(スロット)は「通話で言われうることの役割」で固定し、選択肢は育てる

通話の構造化は、キーワード検索(文脈を失うが集計は簡単)と全文脈保持(集計のたびに全負担)の折衷である。**原文**(発言を逐語で残す)、**構造**(用件ごとに決まった項目へ決まった選択肢から値を入れる)、**根拠**(各値が原文のどこから決まったか)の 3 層を持ち、集計は構造層に対する SQL だけで完結させる。

構造層の項目は「よく聞かれる問い」から逆算しない。問いから作ると問いが増えるたびに項目が足りなくなる。代わりに、顧客の発言を**役割**に分解し、その役割の一覧を項目にする。誰が / 何をした / 何について / その何のどの側面が問題か / なぜ今 / なぜ / どうなった / どう感じた。問いは項目の値の組合せで表せるので、新しい問いは新しいタグではなく新しい組合せになる。**項目は固定し、各項目の選択肢は育てる。** 選択肢を育てる手順(検知 → 候補生成 → 自動検証 → 暫定採用 → 安定化 → 履歴整合)は固定し、人は承認者ではなく拒否権者とする。

### 原則 2: 分析列は閉じた語彙のみ。原文を読み直すのは構造を直すときだけ

分析に使う列はすべて列挙・コード・真偽値。自由記述は (a) 語彙を育てる材料(要約、`other_text`)と (b) 検証用の根拠(逐語引用+位置参照)の 2 用途に限定し、レポートの軸には使わない。すべての列挙列に `other` と `unknown` を持ち、`other` 率を語彙見直しのトリガにする。

**問いに答えるために原文へ LLM を当て直すことはしない。** それをすると LLM を扱える人しか問いを立てられず、民主化の外に出る。原文へ定義文を当てるのは、構造を直すときの 2 場面に限る。(1) 足りない選択肢や項目が実際に件数を持つかを確かめるとき、(2) 足したあとに過去分を埋め直すとき。各選択肢は包含・除外基準の定義文を持ち、その定義文がそのまま埋め直しの指示になる。

### 原則 3: 分析単位は「用件」、原子単位は「ターン」、通話は導出

通話は「あいさつ → 目的発話 → 本人確認 → 議論 → クロージング」という**局面**と、その上を非連続にまたがる**用件**という、直交する 2 つの構造を持つ。通話 1 件 = 1 行ではこの構造が消え、連続区間で切ると 2 つの構造を混同する。

- **ターン**が原子単位。各ターンに局面ラベルと 0〜複数の用件 ID を付ける(ISO 24617-2 の多次元注釈、AMI の機能的/内容的トピックの分離に相当)。
- **用件**が集計単位。reason / outcome / action_items の基本三点と、trigger / confusion などのカスタム事実は用件に付ける。用件は目的発話と議論をまたぎ、本人確認や保留で中断されても同じ ID で復帰する(Grosz & Sidner の焦点スタック)。
- **通話行**は用件と局面から導出する(用件数、主用件、全用件解決、局面ごとの所要、冒頭/末尾の感情)。
- 保留・転送は局面ではなくイベント(タイムレンジ)。

これにより、通話単位では原理的に見えなかった「2 件目以降の用件の内訳」「目的発話で述べられたが議論されなかった用件」「本人確認に費やす割合」が数えられる。

### 原則 4: 品質は「証明」ではなく「担保」する。人手ラベルなしで

絶対精度は証明できないが、次を機械的または数分の作業で担保する。

| 検証 | 防ぐもの |
|---|---|
| 根拠の逐語一致・位置整合 | 幻覚・捏造 |
| 全ターンの局面付与、用件 ID の参照整合、本人確認ターンに用件なし | 帰属の構造ミス |
| 2 モデル間(または言い換えプロンプト間)一致 | プロンプト依存の不安定な判定 |
| 分割半分再現 | ノイズを傾向と誤認 |
| 合成データ回帰 | 抽出器・モデル更新時の劣化 |
| CRM 事実との整合(未解決 → 再入電) | 系統的誤検出 |
| 既知事例の盲検再現 | 分析手順そのものの妥当性 |
| 分析者による根拠 30 件目視 | テーマ定義の過検出。未通過は「未確認」表示 |

加えて、**分析手順(レシピ)が分母・比較期間・両側からの無作為引用・未説明残余を省略できない**形で提供される。結論を書くのは人。ここが「信じ込み」への最も直接的な対策になる。

### 原則 5: 構造で覆えない問いは、スキーマの不備として塞ぐ

社内から来る問いのうち構造層だけで答えられないものは、「答えられない問い」ではなく「直すべき不備」として起票する。不備は 2 種類に分かれ、対処が決まっている。

| 不備 | 例 | 対処 |
|---|---|---|
| 選択肢が足りない(項目はある) | 解約理由に「補償内容への不安」がない | 原則 1 の手順で自動追加し、`other` だった通話だけ埋め直す |
| 項目がない(役割が抜けている) | 「対象のどの側面が問題か」がない | 追加のみの新版を出し、関係しうる通話だけ埋め直す |

埋め直しは差分で行い、既存の項目・集計は変えない。埋め直した結果は別の実行として保存し、どの定義・どのモデルで埋めたかを追えるようにする。到達度の目標は「目録の問いのすべて」であり、「N 件中 M 件」ではない。測るのは「不備を見つけてから塞ぐまでの時間」と、埋め直しの計算負荷である。

## 3. データモデル(スタンドオフ 7 表)

```
turns        (call_id, turn_idx, speaker, text, start_ms, end_ms)
turn_phases  (call_id, turn_idx, phase)            phase ∈ {opening, purpose_statement, verification, discussion, closing, off_topic}
issues       (call_id, issue_id, is_primary, score, reason_l1, reason_l2, trigger_code, touchpoint_code,
              confusion_signal, confusion_type, confusion_touchpoint_code, outcome, action_items[], vocab_version, ...)
issue_turns  (call_id, issue_id, turn_idx)         多対多・非連続可
evidence     (call_id, issue_id, field, turn_idx, begin_char, end_char, quote)
events       (call_id, event_type, start_ms, end_ms)   hold / transfer / system_action
calls        = 上記からの導出ビュー
```

語彙(`reason`, `trigger_code`, `touchpoint_code` など)は抽出プロンプトとは別に注入し、`vocab_version` で管理する。語彙の分割・統合は写像表に残し、任意の過去期間を任意の語彙版で再表現できる。

## 4. 処理の流れ

1. **基盤抽出(全件・バッチ):** 第 1 段でターンごとの局面と用件 ID の帰属、第 2 段で用件ごとに「目的発話+その用件のターン」だけを入力して事実を抽出。入力が絞られるので判定が安定し、本人確認ターンを LLM に渡さずに済む。
2. **機械検証:** §2 原則 4 の構造チェックと逐語一致。不合格行は `evidence_verified = false` として集計から除外または要確認。
3. **語彙進化(週次):** `other` 率の管理図、要約埋め込みの増分クラスタリング、既存タグの分裂・不安定化を検知 → LLM が候補(名前・定義・包含/除外基準・階層位置)を生成 → 規模・持続・分離・一貫性・分割半分再現・階層整合の自動検証 → 暫定採用と差分バックフィル → 安定化で昇格。人は週次ダイジェストに拒否・改名・統合を指示できる。
4. **分析レシピ:** 「急増真因」(時系列 → 期間比較 → 差分順位 → 引用対比 → 仮説再分類 → 反証)と「わかりづらいパターン」(混乱 × 接点 × 下流コスト)。省略不可の工程を持つ。
5. **テーマ定義エンジン(補助):** 語彙にないテーマを一時的に分類するための、バージョン管理された自然言語定義。要約列に対して 10 万件を数分・数百円で再分類。定常レポートには使わず、仮説検証と語彙昇格前の確認に限定。

## 5. できること・できないこと

| できる | できない(別の単位・手段が要る) |
|---|---|
| 用件数ベースの件数・割合・推移・セグメント比較 | 応対品質のコーチング(発話行動の別スキーマ) |
| 急増の真因候補をタグの組み合わせの差として提示 | 語彙にない真因の即時命名(暫定タグで数週間の遅れ) |
| 「わかりづらい」接点と訴え方の特定 | 言い方・温度感の解釈 |
| 述べられたが議論されなかった用件の検出 | 顧客ジャーニー(顧客単位テーブルの追加で対応) |
| 本人確認・保留の所要と位置 | 施策効果の因果的検証(実験設計が要る) |
| 解決状況と再入電の整合チェック | 解約予測(目的変数との結合と学習が要る) |

「この基盤で答えられない問い」の一覧をツールの仕様の一部にする。範囲外の問いは探索層か人の読解に回すと決めておくことが、範囲を広げることと同じくらい重要。

## 6. 先例との関係

構造の各要素には直接の先例がある(05 参照)。ISO 24617-2 の多次元・不連続な注釈単位、AMI の機能的/内容的トピック分離と根拠リンク、Grosz & Sidner の焦点スタック、IBM 2007 / NTT 2018 の通話局面分類、DECODA の不連続テーマ、Oracle 2025 の concern、商用要約の issue / outcome / action item 三点セット、AWS / Google の位置参照付き根拠。v0.3 はこれらの名前・層構造・境界規則・評価指標を借用したものであり、独自部分(ターンと多対多で結びつく用件エンティティ)も CRM の親子ケースに先例がある。
