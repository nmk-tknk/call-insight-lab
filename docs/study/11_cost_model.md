# コストモデル: 全項目を取込時に抽出し、不備のたびに差分再実行する方式は回るか

- 作成日: 2026-09-20
- 背景: 06 原則 2・5(問いに答えるために原文を読み直さない。覆えない問いは不備として塞ぎ、差分で埋め直す)に依頼者が合意したうえで、コスパへの懸念が示された。本書は費用の発生箇所を式にし、設計上の抑制策と、第 1 段(合成 300 件)で実測する項目を定める。
- 前提: 月 10 万件。抽出はローカル LLM を第一候補とするため、費用の主単位は金額ではなく**計算時間**(GPU 時間)。外部 API を使う場合は同じ式のトークン数に単価を掛ける。単価は本書に書かない(変動するため、見積り時に確認する)。

## 0. 要点

- 費用は 5 工程で発生する。支配的なのは**初回抽出**で、月あたりのトークン量は「通話数 × パス数 × 1 件あたりトークン」でほぼ決まる。
- **不備修正の差分再実行は、設計上、初回抽出の数%〜十数%に収まる。** 構造層で対象通話を絞り、用件のターン帰属で入力を絞るためである。この 2 つの絞込みがなければ、不備修正のたびに初回抽出と同額を払うことになり、原則 5 は成立しない。
- 問いのたびに原文を読む方式(廃止した方式)と比べると、同じ問いが 2 回来た時点で差分再実行の方が安い。
- 判断は第 1 段の実測で行う。決め手は「月あたりの GPU 時間が夜間バッチの枠に収まるか」の 1 点。

## 1. 費用が発生する 5 工程

| # | 工程 | 頻度 | 主な変数 |
|---|---|---|---|
| 1 | 初回抽出(局面、用件帰属、全項目) | 全通話、1 回 | N, P, T_in, T_out |
| 2 | 不備修正の差分再実行 | 不備 1 件ごと | k, s, T_in', T_out' |
| 3 | 語彙進化(検知・候補生成・検証) | 週次 | LLM は候補生成と検証のみ。検知は埋め込みで LLM 不要 |
| 4 | 品質ゲート(2 run 一致、合成データ回帰) | 月次 | r_judge |
| 5 | 合成データ生成 | 一度きり | 2,300 件 |

記号:

| 記号 | 意味 | 目安(02 §5 の仮定。第 1 段で実測) |
|---|---|---|
| N | 月の通話数 | 100,000 |
| P | 初回抽出のパス数(一段なら 1。局面 → 用件の二段なら 2 だが、2 パス目は入力を絞れる) | 1〜1.5 |
| T_in | 1 通話の入力トークン(日本語書き起こし + プロンプト固定部) | 4,000〜6,000 |
| T_out | 1 通話の出力トークン(構造 JSON + 根拠引用) | 500〜1,500 |
| k | 月あたりの不備修正回数 | 立上げ期 4〜8、安定期 1〜2 |
| s | 不備 1 件あたり、埋め直す通話の割合(構造層で絞る) | 5〜20% |
| T_in' | 埋め直し 1 件の入力(用件のターンのみ + 短いプロンプト) | T_in の 20〜40% |
| T_out' | 埋め直し 1 件の出力(新項目 1 つ + 根拠) | 50〜150 |
| r_judge | 2 run 一致を掛ける通話の割合(判断列のみ、サンプル) | 5〜10% |
| θ | ローカル LLM の実効スループット(トークン/秒。入力の読込みと出力の生成で桁が違うので分けて測る) | 実測 |

## 2. 月あたりのトークン量

```
初回抽出      = N × P × (T_in + T_out)
差分再実行    = k × s × N × (T_in' + T_out')
2 run 一致    = r_judge × N × (T_in + T_out_judge)
語彙進化      = 候補数 × (数十件のサンプル × T_in) + 検証サンプル × T_in    ← 週次で数百万トークン程度。無視できる規模
```

目安値を入れると(N = 10 万、P = 1、T_in = 5,000、T_out = 1,000):

| 工程 | 入力トークン | 出力トークン | 初回抽出比 |
|---|---|---|---|
| 初回抽出 | 5.0 億 | 1.0 億 | 100% |
| 差分再実行(k = 4、s = 10%、T_in' = 1,500、T_out' = 100) | 0.6 億 | 0.04 億 | 約 11% |
| 差分再実行(安定期 k = 1) | 0.15 億 | 0.01 億 | 約 3% |
| 2 run 一致(r_judge = 10%、判断列のみ出力 300) | 0.5 億 | 0.03 億 | 約 9% |

差分再実行は立上げ期でも初回抽出の 1 割強に収まる。s と T_in' の絞込みが効かない場合(全通話 × 全文で埋め直す)は k × 100% になり、月 4 回の不備修正で初回抽出の 4 倍を払う。**絞込みが原則 5 の成立条件である。**

## 3. 計算時間への換算

ローカル LLM では入力の読込み(prefill)と出力の生成(decode)で速度が桁違いに異なり、通常は出力の生成が支配的になる。月の計算時間は概ね次で見積もる。

```
時間(秒) ≈ 入力トークン / θ_in + 出力トークン / θ_out
```

夜間 8 時間 × 30 日 = 240 時間を枠とすると、初回抽出 + 差分 + 2 run の出力合計 約 1.1 億トークンを 240 時間で処理するには、θ_out ≈ 130 トークン/秒(バッチ処理での合計値)が要る。入力 6 億トークンは θ_in ≈ 700 トークン/秒が要る。これが第 1 段で候補モデルと実行系に求める最低ラインになる。24 時間連続稼働なら各 3 分の 1 で足りる。

θ は、モデルの大きさ、量子化、GPU、バッチ処理の実行系で大きく変わるので、本書では数値を置かない。第 1 段で候補 2〜3 個を実際の環境で測る。

## 4. 設計で費用を抑えている点(すでに入っているもの)

| 抑制策 | 効く変数 | 出所 |
|---|---|---|
| 構造層で対象通話を絞ってから埋め直す(「苦情 × 更新案内」だけ読む) | s | 06 原則 5 |
| 用件のターン帰属を使い、用件レベルの項目は用件のターンだけを入力にする | T_in' | 07 §1-1(用件とターンの多対多) |
| 埋め直しは新項目だけを出力し、既存項目は再抽出しない | T_out' | 08 §8(追加のみ) |
| 2 run 一致は判断列のみ、サンプルのみ | r_judge | 02 §4 |
| 語彙進化の検知は埋め込みと件数で行い、LLM は候補生成と検証だけ | 工程 3 | 04 §1 |
| 根拠は位置参照を主にし、引用は逐語一致検証に必要な最短にする | T_out | 07 §1-7 |

## 5. まだ入っていない抑制策(第 1 段の結果次第で採る)

| 抑制策 | 効く変数 | 条件 |
|---|---|---|
| 項目ごとのモデル分担。局面と用件帰属は良いモデル、行為・対象などの易しい項目は小型モデル | θ | 第 1 段で項目ごとの κ を測り、小型で足りる項目を決める |
| 不備修正を週次で束ね、複数の新項目を 1 パスで埋める | k | 運用 |
| プロンプト固定部の再利用(実行系の KV キャッシュ) | θ_in | 実行系の選定 |
| 安定した項目の蒸留(01 §3.5)。選択肢が安定し LLM ラベルが数万件たまった項目は小型分類器に置き換え、LLM は長尾のみ | 初回抽出の大半 | v1 以降。長尾での崩壊リスク(01 §3.5)があるため、判断列には適用しない |
| 一部の判断列だけ外部 API に出す(マスキング後) | θ | ローカルで κ が足りない列がある場合 |

## 6. 廃止した方式との比較

問いのたびに原文へ定義文を当てる方式(02 §3-②、廃止)は、1 回の問いに s × N × T_in を払う。差分再実行はこれに加えて過去分の埋め直しを 1 回払うが、以後は SQL だけで答える。同じ問い(または同じ項目を使う別の問い)が 2 回来た時点で差分再実行の方が安く、以後は差が開く。加えて、廃止した方式は問いを立てられる人が LLM を扱える人に限られる。

## 7. 第 1 段(合成 300 件)で実測する項目

| 項目 | 測り方 | 判断に使う式 |
|---|---|---|
| T_in, T_out の分布 | 300 件の実トークン数 | §2 |
| θ_in, θ_out | 候補モデル 2〜3 個を実環境でバッチ実行 | §3 |
| P | 一段と二段(局面 → 用件)を同じ 300 件で比較し、精度と時間を並べる(09 X1) | §2 |
| s | 「側面」項目を不備修正として追加し(09 S8)、構造で絞った対象の割合を測る | §2 |
| T_in' | 同上。用件のターンだけを入力にしたときのトークン数 | §2 |
| 項目ごとの κ | ローカル候補 × 外部 API 上位モデル | §5 のモデル分担 |
| 合成データの生成コスト | 300 件の生成トークン数 × 7.7(2,300 件換算) | 工程 5 |

**判断基準**: 月の計算時間(§3)が夜間バッチ 240 時間に収まれば、この方式で進める。収まらなければ §5 の抑制策を上から順に入れ、それでも収まらなければ GPU の増設か一部外部 API を検討する。

## 8. 依頼者への追加質問

- **Q2-e. ローカル LLM を動かす計算資源。** GPU の有無、種類、枚数、メモリ。未定なら「候補の実行環境を借りて測る」で進めるが、θ の実測値は環境に依存するので、本番環境で再測定が要る。
