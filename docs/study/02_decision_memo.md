# 意思決定メモ: 要件を踏まえた「汎用ツールを作る価値」の判断

- 作成日: 2026-09-13
- 前提: `01_llm_structuring_feasibility.md` の調査結果に、以下のヒアリング回答を反映したもの
- 位置づけ: 「作るか / 何を作るか / 何を作らないか」の判断材料

## 0. 反映した要件

| 項目 | 回答 | 設計への影響 |
|---|---|---|
| 通話量 | 月 10 万件 | 全件 LLM 処理は現実的(月数万〜十数万円規模、§5)。人手全数確認は不可能 |
| LLM 利用 | 可 | 抽出・要約・分類に上位モデルを使える |
| 教師データ | なし | 分類体系は LLM 誘導+人の審査で作る。蒸留は当面見送り |
| 分析目的 | (a) 特定テーマの入電増加の真因調査、(b) 「〇〇がわかりづらい」と直接・間接に訴えるパターンの特定 | **記述統計(件数・割合)ではなく診断的分析。** 固定列の単純集計だけでは足りず、分析手順そのものを型にする必要がある |
| 現状の課題 | LLM で誰でも「それっぽい」分析が出せるが、的外れ・歪んだ結果を信じ込む恐れ | **本件の本質は抽出精度ではなく分析品質のガバナンス** |
| 実行環境 | 制約なし | 本メモでは扱わない |
| 人手ラベリング | ほぼ不可能 | 01 で前提にした「数百件の人手ゴールデンセット+PPI 補正」は成立しない。代替の品質担保手段が必要(§4) |
| 完成度 | 社内ツールレベル | UI は最小限。SQL/ノートブック/簡易 Web で十分 |

## 1. 結論

**作る価値はある。ただし「汎用の集計基盤」としてではなく、「分析の手順と根拠を強制する社内ワークベンチ」として作るべき。** 理由は次の 3 点。

1. **課題の本質が「分析品質」であるなら、LLM を自由に使わせる限り解決しない。** 的外れな分析の原因の大半は、抽出ミスではなく分析手順の欠陥(比較対象がない、分母がない、都合のよい引用だけ見る、定義が人によって違う)にある。これは「同じ定義のデータ」と「決まった手順」を通さないと防げない。汎用ツールの価値はここにあり、抽出そのものはコモディティ(DWH の AI 関数でも代替可)。
2. **2 つの分析目的はどちらも、少数の汎用ファセットから組み立てられる。** 「入電増の真因」は「テーマ該当通話の時系列」+「急増期間と平常期間のファセット分布の差分」で構造化できる。「わかりづらい」は横断的な汎用ファセット(`confusion_signal` とその対象)として抽出できる。つまり目的固有のものは薄く、共通基盤は厚い。
3. **人手ラベリングなしでも、品質を「証明」はできないが「担保」はできる。** 根拠引用の機械検証、複数モデル一致、合成データ回帰、外部指標との整合、既知事例での再現テスト、そして分析者による根拠 30 件の目視。これらは全て自動化または数分の作業で回る(§4)。

一方で、**作るべきでないもの**も明確になった。

- 50 列級の網羅的スキーマ(精度が崩れ、誰も定義を追えない)
- 「何でも聞ける」自然言語インターフェースを主機能にすること(再現性のない結果を量産し、現状の課題を再生産する)
- 人手ラベル前提の精度保証機構(回らない)

## 2. 分析目的の構造分解

### 2.1 目的 (a): 特定テーマの入電増加の真因調査

分析者が実際にやるべき手順を書き下すと次のようになる。ここで LLM が必要なのは太字の箇所だけで、残りは通常の集計と比較である。

1. テーマを定義する(例: 「請求金額に関する問い合わせ」)。**自然言語の定義文(包含基準・除外基準・境界例)を LLM が各通話に適用**し、該当フラグを付ける。
2. 該当件数の時系列を出し、急増期間と比較用の平常期間を決める。**分母(総入電数)で正規化する。**
3. 急増期間と平常期間で、該当通話のファセット分布を比較する。用件サブカテゴリ、きっかけ(通知書を受け取った、アプリ更新、料金改定、報道…)、対象商品、顧客属性、チャネル、解決状況、混乱の対象。差が大きい順に並べ、効果量と信頼区間を出す。
4. 差が大きい軸について、**両期間から無作為抽出した根拠引用を並べて読む。** ここで仮説が立つ(「9 月の改定通知の文面 X が誤解を生んでいる」等)。
5. 仮説を検証する。**仮説を新しいテーマ定義として再分類**し、時系列が急増と一致するか、急増期間に集中しているかを確認する。
6. 反証を探す。仮説に該当しない急増分がどれだけ残るかを示す。

「誰でもそれっぽい分析」は、この手順の 2(分母)、3(比較対象)、6(反証)を飛ばして 4(引用)だけをやることで生まれる。ツールはこの手順を**飛ばせない形**で提供する。

### 2.2 目的 (b): 「わかりづらい」と訴えるパターンの特定

「わかりづらい」は特定テーマではなく、あらゆる用件に横断する**信号**である。したがって全通話に対して常時抽出する汎用ファセットにするのが正しい。

| 列 | 内容 |
|---|---|
| `confusion_signal` | 顧客が理解困難・誤解・確認を表明しているか(bool) |
| `confusion_type` | direct(「わかりにくい」と明言)/ indirect_misread(誤解した状態で入電)/ indirect_clarify(既に案内済みの内容を確認するための入電)/ none |
| `confusion_object` | 何がわかりづらかったか(自由記述 1 句: 「請求書の内訳欄」「アプリの解約導線」「〇〇という用語」) |
| `confusion_evidence` | 根拠となる顧客発話の逐語引用 |

分析は「`confusion_signal` = true の通話を `confusion_object` でクラスタリングし、件数・推移・下流コスト(再入電、通話時間、エスカレーション)で順位付けし、各クラスタの根拠引用を読む」で完結する。ここで重要なのは、**indirect の検出こそが LLM を使う意味**であり、キーワード検索では拾えない部分である。同時に、indirect は LLM が最も過検出しやすい部分でもあるため、§4 の検証対象の筆頭になる。

### 2.3 共通基盤として必要な汎用ファセット(v0 改訂)

01 の v0 案から、2 つの目的に効く列だけに絞り、「きっかけ」と「混乱」を追加した。

| 列 | 型 | 目的 (a) | 目的 (b) |
|---|---|---|---|
| `request_summary` | 自由記述 1 文 | テーマ再分類の入力 | クラスタリングの入力 |
| `reason_l1/l2` | 列挙(LLM 誘導、`other` あり) | 比較軸 | 比較軸 |
| `trigger` | 列挙+自由記述(通知書受領/アプリ更新/請求確認/報道/他者から聞いた/不明) | **真因の最短経路** | 補助 |
| `product_or_service` | 列挙 or 自由記述 | 比較軸 | 比較軸 |
| `resolution_status` | 列挙 | 補助 | 下流コスト |
| `confusion_signal/type/object/evidence` | 上記 | 比較軸 | **主対象** |
| `customer_emotion_end` | 3 段階 | 補助 | 補助 |
| メタ(`schema_version`, `prompt_version`, `model`, `extracted_at`) | | 再現性 | 再現性 |

10 列前後。判断項目(`resolution_status`, `confusion_signal`)には推論欄を先行させ、すべての判断に逐語引用を必須にする。

## 3. 作るもの: 4 つの構成要素

```mermaid
flowchart TB
  subgraph L1[① 基盤抽出(月次バッチ、全 10 万件)]
    T[書き起こし] --> F[汎用ファセット抽出<br/>10 列 + 逐語引用]
    F --> Q1[自動検証: 引用の逐語一致<br/>スキーマ準拠 / 分布監視]
  end
  subgraph L2[② テーマ定義エンジン]
    D[分析者が定義文を書く<br/>包含 / 除外 / 境界例] --> C[request_summary に適用<br/>10 万件を数分・数百円で再分類]
    C --> V[定義はバージョン付きで保存・共有<br/>誰が実行しても同じ結果]
  end
  subgraph L3[③ 分析レシピ]
    R1[急増真因レシピ<br/>時系列 → 期間比較 → 差分順位 → 引用対比 → 仮説再分類 → 反証]
    R2[混乱パターンレシピ<br/>confusion 抽出 → 対象クラスタ → 件数・推移・下流コスト → 引用]
  end
  subgraph L4[④ 品質ゲート]
    G[根拠 30 件目視 / 複数モデル一致 / 分割半分再現 /<br/>合成データ回帰 / 外部指標整合 / 既知事例再現]
  end
  L1 --> L2 --> L3 --> L4
  L4 -->|確認済みラベル| OUT[共有される分析結果<br/>定義・手順・根拠・検証結果が全て添付]
```

### ① 基盤抽出

月次(または日次)バッチで全通話に汎用ファセットを付与。出力は通話 1 件 = 1 行のテーブル。引用列は**書き起こし本文との逐語一致を機械的に検証**し、一致しない行は `evidence_verified = false` として集計から除外または要確認にする。これは人手なしで幻覚を検出できる最も強い自動チェックである。

### ② テーマ定義エンジン(「自由な LLM 利用」の受け皿)

「好き勝手に LLM を使う」需要を否定せず、**定義文というバージョン管理された成果物に変換する**のがこの層の役割。

- 分析者は自然言語で「このテーマに含まれる通話 / 含まれない通話 / 境界例」を書く(LLooM の包含基準の考え方)。
- 適用対象は書き起こし全文ではなく `request_summary`(+必要なら `confusion_object`)。10 万件 × 約 150 トークン = 約 1,500 万トークンで、費用は数百円〜数千円、所要は数分。**全文を読み直す方式に比べ 20〜30 分の 1 のコストで、対話的に試行錯誤できる。**
- 定義文・モデル・実行日時・結果件数は保存され、他の人が同じ定義を再実行すれば同じ結果になる。定義文の差分がそのまま「なぜ数字が違うか」の説明になる。
- 全文を見ないと判定できないテーマ(発話の細部に依存するもの)は、要約での粗選別→該当候補のみ全文で精査、の 2 段にする。

### ③ 分析レシピ

§2.1 と §2.2 の手順をそのまま実装する。レシピは以下を**省略できない**:

- 分母(期間ごとの総入電数)と正規化後の割合
- 比較対象期間の明示
- 差分の効果量と信頼区間(件数ベースの通常の統計。LLM 誤差は§4 の別枠で扱う)
- 両側からの無作為抽出引用(都合のよい引用の排除)
- 反証(仮説で説明できない残余の大きさ)

出力は「結論」ではなく「比較表+引用+未説明残余」であり、結論を書くのは人。これが「信じ込み」への最も直接的な対策になる。

### ④ 品質ゲート(§4)

## 4. 人手ラベリングなしで分析品質を担保する方法

01 で前提にした「数百件の人手ラベル+PPI 補正」は使えない。代わりに、**自動化できる検証**と**分析者が数分でできる検証**を組み合わせる。正直に言えば、これで絶対精度を証明することはできない。証明できるのは「根拠がある」「安定している」「外部事実と矛盾しない」「既知の事例を再現できる」であり、それで「的外れな分析を信じ込む」リスクの大半は潰せる。

| 検証 | 何を防ぐか | コスト | 自動化 |
|---|---|---|---|
| **引用の逐語一致検証** | 根拠の捏造、要約の幻覚 | ゼロ | 完全自動 |
| **複数モデル一致(または同一モデルの言い換えプロンプト一致)** | プロンプト依存の不安定な判定。一致率が低い列・テーマは「不安定」と表示し、そのテーマでの結論を保留させる | LLM 費用 2 倍(該当列のみ) | 完全自動 |
| **分割半分再現** | ノイズを傾向と誤認すること。無作為に二分した半分ずつで同じ差分・同じ順位が出るか | ゼロ | 完全自動 |
| **合成データ回帰** | 抽出器の劣化、モデル更新時の挙動変化。既知ラベル付きの合成通話(混乱あり/なし、テーマ該当/非該当、境界例)を数百件生成し、再現率・適合率を継続監視(Clio が 94% 復元を示したのと同じ手法) | 初期構築のみ | 完全自動 |
| **外部指標との整合** | 系統的な誤検出。`resolution_status = unresolved` が 7 日以内の再入電を予測するか、`confusion_signal` が通話時間・転送率と相関するか。相関がなければ列の定義を疑う | CRM 結合のみ | 完全自動 |
| **既知事例での再現テスト** | レシピ自体の妥当性。過去に真因が判明している入電増を 2〜3 件選び、真因を伏せてレシピを回し、上位仮説に真因が入るか | 事例の選定のみ | 半自動 |
| **分析者による根拠 30 件目視** | テーマ定義の過検出。フラグ通話 30 件の引用を読んで該当率を記録(≒その分析における適合率)。近傍の非該当 20 件も読み、取りこぼしを確認 | 10〜15 分 / 分析 | 人 |
| **`other` 率・分布のドリフト監視** | スキーマの陳腐化 | ゼロ | 完全自動 |

運用ルールとして、**根拠 30 件目視を通過していない分析結果は「未確認」ラベルのまま共有され、意思決定資料には使えない**、とする。これは「人手ラベリング」ではなく分析者自身の確認作業であり、月 10 万件のラベリングとは別物。実行可能な範囲に収まる。

残るリスクも明記する。

- 全モデルが共有する系統バイアス(例: 日本語の丁寧な確認表現を一律に「混乱」と判定する)は複数モデル一致では検出できない。合成データの境界例と、根拠目視で拾う。
- ファセットに現れない交絡(同時期の別施策など)はツールでは見えない。反証ステップで「未説明残余」として可視化するに留まる。
- 抽出精度の絶対値は不明のまま。「割合」の絶対水準より「期間差・順位」の相対比較を主用途にする設計が、この弱点と整合している。

## 5. 費用と工数の目安(要確認)

- **基盤抽出:** 1 通話あたり入力 4〜6k トークン(日本語書き起こし)+出力 500 トークンと仮定。月 10 万件で、中位モデル(入力 $1 / 出力 $5 相当)なら月およそ $750〜1,000、バッチ API で半額。小型モデルなら月 $100 前後。上位モデルで月 $3,000 前後。複数モデル一致を判断列のみに掛けても 1.5 倍程度。
- **テーマ再分類:** 1 回あたり数百円〜数千円。分析者が 1 日に何度回しても問題ない。
- **構築工数:** PoC(基盤抽出+テーマエンジン+急増レシピ 1 本+品質ゲートの自動部分)で 1〜2 人 × 4〜6 週間。社内ツールとしての v1 で 2〜3 か月。
- 比較対象として、01 の商用製品はこの 2 つの分析目的(真因調査、混乱パターン)を直接は提供していない。ダッシュボードと「AI に質問」が中心で、手順の強制や検証ゲートを持つ製品は見当たらなかった。社内で作る根拠はここにある。

## 6. Go / No-Go の判断基準(PoC で確認すること)

人手ラベルなしで判断できる基準に限定する。

| 基準 | 合格ライン(案) |
|---|---|
| 引用の逐語一致率 | 98% 以上 |
| 合成データでの `confusion_signal`・テーマ該当の再現率/適合率 | ともに 0.9 以上、境界例で 0.8 以上 |
| 判断列の複数モデル一致(κ) | 0.7 以上。下回る列は v1 から外す |
| 外部整合 | `unresolved` の 7 日内再入電率が全体の 1.5 倍以上 |
| 既知事例の再現 | 2〜3 件中、真因が上位 3 仮説に入るのが 2 件以上 |
| 分析者の根拠目視 | 実テーマ 2 本で該当率 0.8 以上 |
| 分析者の体感 | 「自分で LLM に聞くより信頼できる結果が、同等以下の手間で出る」と 2 名以上が答える |

**既知事例の再現に失敗した場合は、レシピの設計(比較軸・ファセット)を疑う。** 抽出精度が高くても真因に届かないなら、それは「汎用ファセットで真因が表現できていない」ことを意味し、`trigger` 列などの追加で改善するか、この目的には向かないかを判断する材料になる。

## 7. 汎用性についての最終的な見立て

- **汎用にできる部分(厚い):** 基盤ファセット抽出、テーマ定義エンジン、品質ゲート、期間比較の統計。これらは目的が変わっても再利用される。
- **目的ごとに作る部分(薄い):** 分析レシピ。ただしレシピは「比較軸を選び、順に表示する」程度の薄さで、1 本あたり数日で追加できる。
- **汎用にしてはいけない部分:** 結論を出す工程。ここを LLM に委ねると現状の課題に戻る。

したがって「様々な分析目的に汎用で使えるものを作る」は、**「汎用の答えを出す装置」なら筋が悪く、「汎用の証拠と手順を用意し、答えは人が出す装置」なら筋が良い**、が最終的な見立てである。

## 8. 次のアクション

1. 既知の過去事例(真因が判明している入電増)を 2〜3 件、テーマと期間だけ特定する。真因は PoC 実施者に伏せる。
2. サンプル 2,000〜5,000 件(急増期間と平常期間を含む)で基盤抽出を実行し、§6 の自動基準を測る。
3. 急増真因レシピを 1 本実装し、既知事例で盲検テストを行う。
4. 混乱パターンレシピで `confusion_type = indirect_*` の根拠を 30 件読み、過検出の度合いを確認する。
5. 結果をもって v1 の Go / No-Go を判断する。
