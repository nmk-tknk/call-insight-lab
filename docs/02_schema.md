## 1. 要点

- **LLM が注釈層に書くのは 2 種類だけ**: 構造(局面、用件の切り出し、ターン帰属)と、発話行為(誰が何を明言したか。必ず引用付き)。
- **混乱の型・動機・結果・受容・横断フラグ・感情は保存しない。** 発話行為と業務知識表(既知の誤解一覧)から SQL のビューで導く。分析用ビューの列名は v0.3.1 と同じなので、既存の集計はそのまま動く。
- **判断の定義を変えても再抽出は要らない。** ビューの SQL を直すだけで、過去分も含めて数字が変わる。差分再実行が要るのは、明言の種類や対象が語彙に足りないときだけになる。
- **感情は表出のみ。** 「腹が立つ」「助かりました」は事実として記録し、口調からの推定はしない。

v0.4 の理由(案)は 3 つ。(1) **再現性**: 「なぜこの通話が誤解と数えられたか」が、LLM の判断ではなく「主張 A にオペレータの訂正 B が続いた」という規則で説明できる。(2) **変更の安さ**: 判断の定義は必ず揺れる。ビューに置けば、定義を直すのは SQL の修正で済み、10 万件を LLM に回し直す必要がない。(3) **抽出の易しさ**: 明言の記録は引用の逐語一致で全件を機械検証でき、小型モデルの守備範囲が広がる。2 run 一致が要るのは構造だけになる。

例外は構造(用件の切り出し、帰属、局面の境界)である。これは明言ではなく対話構造の解釈で、集計時には導けない。主観の度合いは低く、参照整合と 2 run 一致で機械的に検証できるので、注釈層に残す。失うのは明言されていない含意だけで、どれだけ失うかは PoC 第 1 段で「推論あり抽出」と比較して測る([05_poc_plan.md](05_poc_plan.md) §5)。

## 4. 発話行為と導出規則

### 4.1 発話行為の語彙

「誰が / 何をした / 何について / どの側面 / 値 / 引用」を 1 行とする。値は行為ごとに閉じた語彙を持つ。発話行為の種類は業種によらない役割の一覧で、問いの有無にかかわらず常に全種類を抽出する(案。[open_issues.md](open_issues.md) A7)。「主張する」の値を主張コード(業種固有の誤解一覧)で持つ方式は、2026-09-22 に依頼者が「語彙に該当がない」前提自体に疑義を示しており、扱いは未決([open_issues.md](open_issues.md) S17)。

| 話者 | 行為 | 値の語彙 | 導く判断列 |
|---|---|---|---|
| 顧客 | 照会する / 変更を依頼する / 申し込む / 解約する / 不具合を報告する / 苦情を言う / 確認する / 提案する | — | 行為 × 対象 × 側面(用件の主たる行為) |
| 顧客 | 経緯を述べる | きっかけ | きっかけ、きっかけの対象、経路 |
| 顧客 | 理由を述べる | 動機 | 動機(述べなければ不明) |
| 顧客 | 主張する(事実についての認識。正誤は問わない) | 主張コード | 間接的な誤解(訂正が続く、または既知の誤解一覧にある) |
| 顧客 | 理解困難を表明する | — | 直接の混乱 |
| 顧客 | 案内済みに言及する | — | 確認のための入電 |
| 顧客 | 了承する / 不服を述べる | — | 受容、混乱の解消、結果 |
| 顧客 | 以前の連絡に言及する | — | 再入電の示唆 |
| 顧客 | 感情を表出する | 怒り / 不満 / 不安 / 困惑 / 感謝 / 安堵 | 通話の開始時・終了時の感情(表出のみから) |
| 顧客 | 意向を表明する | 解約 / 他社乗換え / 継続 | 解約の兆し |
| 顧客 | 上席を求める / 暴言・脅迫 / 制約を述べる / 知らなかったと述べる / 数量を述べる | — | 横断フラグ、数量 |
| オペレータ | 説明した / 訂正した / 再発行した / 変更した / 上席に上げた / 折返しを約束した / 断った / Web を案内した / 引き止めを提案した | — | オペレータ行動、結果、間接的な誤解(訂正) |
| オペレータ | 断定的に保証した / 謝罪した / 保留した / 転送した / 本人確認した | — | コンプライアンス懸念、保留・転送の注釈、局面の補助 |

側面(`aspect`)の値: 時期 / 金額 / 記載内容 / 届き方 / 適用範囲 / 手続き・操作 / 見やすさ / その他。

### 4.2 導出規則(`v_issue_derived` ほか)

「わかりづらい」は特定テーマではなく、あらゆる用件に横断する信号として全通話から導く。訴え方は、直接(「わかりにくい」と明言)/ 間接・誤解(誤解した状態で入電)/ 間接・確認(既に案内済みの内容を確認するための入電)の 3 つに分ける。間接の検出が LLM を使う意味であり、同時に最も過検出しやすい部分でもあるため、品質ゲートの検証対象の筆頭になる([05_poc_plan.md](05_poc_plan.md) §3)。

| 判断列 | 規則 |
|---|---|
| きっかけ | 顧客の「経緯を述べる」の値。なければ不明 |
| 動機 | 顧客の「理由を述べる」の値。なければ不明。**推し量らない** |
| 混乱の型 | 「理解困難の表明」があれば直接。なければ「主張」に (a) 同一用件で後続するオペレータの「訂正」があるか、(b) 主張コードが既知の誤解一覧にあれば、間接(誤解)。なければ「案内済みへの言及」があれば間接(確認)。それ以外は none |
| 混乱の対象 | 採用した行為の対象 |
| 混乱の解消 | 混乱の行為より後に「了承」があれば解消、「不服」があれば未解消、どちらもなければ不明 |
| 受容 | 顧客の最後の「了承 / 不服」。相槌だけの「はい」は了承と数えない(語彙の除外基準) |
| 結果 | オペレータの「上席に上げた」→ 上席移管。「折返し約束」→ 折返し。「説明・変更・再発行・Web 案内」があり不服がなければ解決。不服がある、または対応行為がなければ未解決。それ以外は不明 |
| 再入電の示唆 | 「以前の連絡に言及」があれば真 |
| 側面 | 用件の主たる依頼行為の側面 |
| 横断フラグ | 意向表明(解約 / 乗換え)→ 解約の兆し。暴言 → ハラスメント。オペレータの断定的保証 → コンプライアンス懸念。上席要求。感謝の表出 → 称賛。制約 → 利用上の制約。知らなかった → Web 手続きの不認知 |
| 感情(通話) | 最初の 25% のターンの表出から開始時、最後の 25% から終了時。否定的な表出があれば negative、なければ肯定的があれば positive、なければ neutral |
| 保留・転送 | オペレータの「保留 / 転送」の発話から。時間はターン時刻で近似 |

規則はこのビューが唯一の定義であり、変更は語彙版と同じく履歴に残す。数字は「不服 N / 了承 M / 不明 K」のように、不明を必ず分けて出す。

## 5. 業務知識表

`known_misconceptions`(既知の誤解一覧)は、業務側が保守する表である。「顧客がこう主張したら、それは誤解である」を主張コードで持ち、正しい事実を添える。オペレータの訂正がなくても、この表に載っていれば誤解と数える。初期値として自動車保険の 8 件(等級が上がれば必ず下がる、無事故なら上がらない、ゴールドは即反映、控除対象、別居の子も家族、証券不着は未契約、二重請求、年齢条件は記名被保険者のみ)を置いた。正誤と保守担当は依頼者の確認待ち([open_issues.md](open_issues.md))。この表を直すことも、LLM を回さずに数字を変える手段になる。

v0.4.1 で追加予定の業務知識表・値([open_issues.md](open_issues.md) S14〜S16): 業務側の変更の登録先 `business_changes`、経緯の複数化と「Web で試した」のきっかけ、「断った」の理由と案内先。

## 7. 取込時にしか得られない情報

原文(書き起こし)に含まれず、再注釈では戻らない情報。v0.3.1 で列は用意したが、業務メタデータがない([01_concept.md](01_concept.md) R3)ため当面は空のまま。実データを取り込む時点で、取込パイプラインに含めるかを決める。決めなければ、決めるまでの期間のデータは永久に欠ける。

| 情報 | 列 | 効く分析 |
|---|---|---|
| 着信経路(IVR 選択、キュー、待ち時間、発着信区別) | `calls.direction / queue / ivr_path / wait_sec` | 急増の切り分け(IVR 選択と用件のずれ) |
| 通話の終了理由(顧客切断 / オペレータ終了 / 途中切断 / 転送で終了) | `calls.end_reason` | 未解決の解釈、再入電の予測 |
| CRM ケース ID・後処理コード | `calls.external_case_id / disposition_code` | 既存分類との突合、再入電判定 |
| ASR のターン別信頼度 | `turns.asr_confidence`(任意で単語別) | 数字・固有名詞の誤りの検出 |
| 転送後のオペレータ | `events.agent_id` | オペレータ別分析 |
| 顧客属性の時点スナップショット | `call_customer_snapshot` | セグメント比較。CRM に時点履歴がなければ取込時に保存 |
| ターン時刻、オペレータ ID、顧客 ID | `turns.start_ms / end_ms`, `calls.agent_id / customer_id` | 通話時間、オペレータ別、再入電の突合。書き起こしファイルに含まれるかは確認待ち([open_issues.md](open_issues.md)) |
| パラ言語、ASR の代替候補、音声そのもの、チャット固有の情報 | なし | 要件が出たら追加 |

## 8. 与えられる保証の正確な言い方

- 「情報が落ちない」保証はできない。構造化は定義上、情報を落とす。
- 言えるのは 4 点。(1) 書き起こしの範囲で原文は無損失に残る。(2) 注釈層の発話行為はすべて原文の位置を指し、逐語一致で機械検証できる。構造(局面、帰属)は引用を持たないが、参照整合と 2 run 一致で検証する。(3) 注釈層にない情報は新しい表と run で後から追加でき、既存の集計は壊れない。(4) 取込時にしか得られない情報は §7 の列を取込設計に含めれば失われない。
- 残る本質的な損失は、閉じた語彙に潰す時点で消えるニュアンスと、明言されていない含意(不明として数える)であり、原文と根拠引用へのドリルダウンで補う。

## 9. 処理の流れ(案)

1. **取込**: 書き起こしをマスキングし(ローカル)、原文層に保存する。マスキングの位置と種別を残す。
2. **基盤抽出(全件・バッチ)**: 第 1 段でターンごとの局面と用件 ID の帰属、第 2 段で用件ごとに「目的発話+その用件のターン」だけを入力して発話行為を抽出する。入力が絞られるので判定が安定し、本人確認ターンを LLM に渡さずに済む。段数は未決([open_issues.md](open_issues.md) X1)。
3. **機械検証**: §6 の不変条件と逐語一致。不合格行は集計から除外または要確認。
4. **導出**: 発話行為と業務知識表から、混乱・動機・結果・受容・横断フラグ・感情を SQL のビューで導く(§4.2)。
5. **語彙の保守**: 旧案は週次の語彙進化ループ([03_vocabulary.md](03_vocabulary.md) §2)。「語彙に該当がない」を常態とする前提に依頼者が疑義を示したため、扱いは未決([open_issues.md](open_issues.md) S17)。
6. **分析レシピ**: [04_analysis_needs.md](04_analysis_needs.md) §5。省略不可の工程を持つ。

## 10. 構造の定義: 局面と用件(案)

通話は「あいさつ → 目的発話 → 本人確認 → 議論 → クロージング」という**局面**と、その上を非連続にまたがる**用件**という、直交する 2 つの構造を持つ。通話 1 件 = 1 行ではこの構造が消え、連続区間で切ると 2 つの構造を混同する。

- **ターン**が原子単位。各ターンに局面ラベルと 0〜複数の用件 ID を付ける(ISO 24617-2 の多次元注釈、AMI の機能的/内容的トピックの分離に相当)。
- **用件**が集計単位。用件は目的発話と議論をまたぎ、本人確認や保留で中断されても同じ ID で復帰する(Grosz & Sidner の焦点スタック)。用件の定義と粒度は [04_analysis_needs.md](04_analysis_needs.md) §0.5。
- **通話行**は用件と局面から導出する(用件数、主用件、全用件解決、局面ごとの所要、冒頭/末尾の感情表出)。
- 保留・転送は局面ではなくイベント。

これにより、通話単位では原理的に見えなかった「2 件目以降の用件の内訳」「述べられたが議論されなかった用件(取りこぼし)」「本人確認に費やす割合」が数えられる。先例は [reference/prior_art.md](reference/prior_art.md)。

## 11. 列の規約(案)

分析に使う列はすべて列挙・コード・真偽値。自由記述は (a) 語彙の材料(要約、`other_text`)と (b) 検証用の根拠(逐語引用+位置参照)の 2 用途に限定し、レポートの軸には使わない。すべての列挙列に `other` と `unknown` を持つ。`other` の扱い(語彙見直しのトリガとするか、失敗の警報とするか)は未決([open_issues.md](open_issues.md) S17)。

原文へ定義文を当てるのは、構造を直すときの 2 場面に限る。(1) 足りない選択肢や項目が実際に件数を持つかを確かめるとき、(2) 足したあとに過去分を埋め直すとき。各選択肢は包含・除外基準の定義文を持ち、その定義文がそのまま埋め直しの指示になる(帰結 2 として依頼者の了解を得た運用。[01_concept.md](01_concept.md) M4)。
