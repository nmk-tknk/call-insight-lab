# A. 外部 API 利用前提の見積り

## A0. 要点

- **月 10 万件の全項目抽出は、中位モデルのバッチ利用で月 1,000〜1,100 USD、小型モデルなら 150〜500 USD。** 不備修正の差分再実行と 2 run 一致を足しても 1.2 倍程度(§A3)。
- 費用の支配項は初回抽出であり、その中では**出力トークン**(構造 JSON + 根拠引用)が入力と同程度を占める。根拠引用を最短にすることが単価選び以上に効く。
- PoC(合成 2,300 件の生成と、300 件 × 5 モデルの比較)は**一度きりで 300 USD 未満**(§A6)。
- 必要な性能帯は列によって異なる(§A4)。構造の骨格(局面境界、非連続な用件帰属)は中位以上、発話行為(明言の記録)は小型で足りる見込み。第 1 段の κ で列ごとに確定する。

## A1. 単価(1M トークンあたり USD)

バッチ API は 3 社とも標準単価の 50% 引き。プロンプトキャッシュ(固定部の再利用)は Claude で読取 0.1 倍、OpenAI で 0.1 倍と報じられている。バッチ内でのキャッシュ命中は保証されないため、本見積りではキャッシュ効果を見込まない(見込めば固定部 1〜2k トークン分がさらに下がる)。

| Claude Sonnet 5 | 2.00 / 10.00 | 1.00 / 5.00 | 公式(導入価格が恒久化) |
| Claude Haiku 4.5 | 1.00 / 5.00 | 0.50 / 2.50 | 公式 |
| GPT-5.5 | 5.00 / 30.00 | 2.50 / 15.00 | 第三者集計、要確認 |

| GPT-5 mini | 0.25 / 2.00 | 0.125 / 1.00 | 第三者集計、要確認 |
| Gemini 3.1 Pro | 2.00 / 12.00(200k 超は 4 / 18) | 1.00 / 6.00 | 第三者集計、要確認 |

注: Claude の 4.7 以降のモデルは新しいトークナイザで、同じ文章に対しトークン数が約 30% 多くなると公式に記載がある。日本語書き起こしのトークン数はベンダーごとに異なるので、下の T_in / T_out は共通の仮置きであり、第 1 段で各社の実測値に置き換える。

**文字数への換算(目安)。** 日本語の会話文は、現行の主要トークナイザで概ね 1 トークン = 1〜1.5 文字(ひらがな主体の話し言葉は 1 文字寄り、漢字が多い書き言葉は 1.5 文字寄り)。英語の 1 トークン ≈ 4 文字と違い、日本語はほぼ文字数がトークン数になると考えてよい。

| 仮置き | 内訳 | 文字数の目安 | 通話時間の目安(会話 250〜350 文字/分) |
|---|---|---|---|
| 入力 5,000 トークン | 書き起こし約 4,000 + プロンプト固定部(指示文・語彙・スキーマ)約 1,000 | 書き起こし 4,000〜6,000 文字 | 12〜20 分の通話 |
| 出力 1,000 トークン | 構造 JSON(キーとコードは英数字で 3〜4 文字/トークン)+ 根拠引用と要約(日本語で 1〜1.5 文字/トークン) | 2,500〜3,500 文字の JSON。用件 2 件 × (項目 12 個 + 引用 5 本 × 30 文字 + 要約 40 文字)程度 | — |

本環境では各社の計数 API とトークナイザに到達できなかったため、上は一般的な比率からの換算である。第 1 段の最初の作業として、合成 300 件を各社の計数 API に掛けて置き換える。`poc/samples` の 19 件は平均 325 文字の要約的な台本で、実通話の長さを表していない。合成データは [05_poc_plan.md](05_poc_plan.md) §2.4 で通話時間の分布を指定して生成する。

## A2. 1 通話あたりと月額(初回抽出のみ)

仮定: N = 10 万件、T_in = 5,000(書き起こし約 4k + プロンプト固定部約 1k)、T_out = 1,000(構造 JSON + 根拠引用)、バッチ API、キャッシュ効果なし。

| モデル | 1 通話 | 初回抽出 月額 | 差分再実行 + 2 run 込み(× 1.2、§A3) |
|---|---|---|---|
| Claude Opus 5 | 0.0250 | 2,500 | 3,000 |
| Claude Sonnet 5 | 0.0100 | 1,000 | 1,200 |
| Claude Haiku 4.5 | 0.0050 | 500 | 600 |
| GPT-5.5 | 0.0275 | 2,750 | 3,300 |
| GPT-5 | 0.0081 | 810 | 980 |
| GPT-5 mini | 0.0016 | 160 | 200 |
| Gemini 3.1 Pro | 0.0110 | 1,100 | 1,320 |
| Gemini 3 Flash | 0.0028 | 275 | 330 |
| Gemini 3.1 Flash-Lite | 0.0014 | 140 | 165 |

感度: T_out が 1,000 → 500 に減ると(根拠引用を最短化)、どのモデルでも月額は約 25〜35% 下がる。T_in が 5,000 → 7,000 に増えると(長い通話、トークナイザ差)、約 20〜30% 上がる。

## A3. 初回抽出以外の工程

§B2 の式と同じ。目安値(k = 4、s = 10%、T_in' = 1,500、T_out' = 100、r_judge = 10%)では、差分再実行が初回の約 11%、2 run 一致が約 9%。合わせて初回の 1.2 倍を月額の上限目安とする。語彙進化の LLM 利用(候補生成と検証)は月数百万トークンで、上の表の 1% 未満。

2 run 一致の 2 本目は別ベンダーの同格モデルにすると、同系モデルの共通バイアスを避けられる。費用は構造のみ・10% サンプルなので、どの組合せでも月 100〜300 USD に収まる。

## A4. 必要な性能帯(列ごと)

| 列の群 | 何が難しいか | 必要な性能帯 | 候補 |
|---|---|---|---|
| 構造の骨格: 局面の境界、用件の切り出し、非連続なターン帰属 | 4〜6k トークンの日本語対話全体を見て、話題の復帰を追う。ここを誤ると以後の全列と差分再実行が崩れる | **中位以上**。一度作れば埋め直しでも再利用するので、ここに費用を掛ける価値が最も高い | Sonnet 5 / GPT-5 / Gemini 3.1 Pro |
| 発話行為(明言の記録): 依頼、主張、理由の陳述、了承 / 不服、オペレータ行動など | 閉じた語彙への当てはめと引用の切り出し。定義文と選択肢が与えられれば難度は低い。判断列は保存せず SQL で導くため、抽出側に判断はない([02_schema.md](02_schema.md) §4) | **小型で足りる見込み**。第 1 段で確認 | Haiku 4.5 / GPT-5 mini / Gemini 3 Flash。基準測定は Opus 5 / GPT-5.5 |
| 根拠引用(位置参照) | 逐語一致の正確さ。構造化出力で文字位置を返す | 小型で足りる。誤りは機械検証(I4、I10)で弾ける | 同上 |
| マスキング(取込) | 個人情報の再現率。マスキング前は外部に出せない | **外部 API は使えない**。規則 + NER、またはローカル | — |
| 合成台本の生成(一度きり) | 自然な日本語の対話。抽出モデルと別にする | 中位以上。品質が高いほど抽出の評価が厳しくなる | Sonnet 5 または Opus 5。抽出に Claude を使うなら生成は他社にする |

構造化出力(JSON スキーマ制約)は 3 社とも提供しており、閉じた語彙の準拠はスキーマ側で担保できる。

# B. ローカル LLM を使う場合(参考)

## B0. 要点

- 費用は 5 工程で発生する。支配的なのは**初回抽出**で、月あたりのトークン量は「通話数 × パス数 × 1 件あたりトークン」でほぼ決まる。
- **不備修正の差分再実行は、設計上、初回抽出の数%〜十数%に収まる。** 構造層で対象通話を絞り、用件のターン帰属で入力を絞るためである。この 2 つの絞込みがなければ、不備修正のたびに初回抽出と同額を払うことになり、原則 5 は成立しない。
- 問いのたびに原文を読む方式(廃止した方式)と比べると、同じ問いが 2 回来た時点で差分再実行の方が安い。
- 判断は第 1 段の実測で行う。決め手は「月あたりの GPU 時間が夜間バッチの枠に収まるか」の 1 点。

## B1. 費用が発生する 5 工程

| # | 工程 | 頻度 | 主な変数 |
|---|---|---|---|
| 1 | 初回抽出(局面、用件帰属、発話行為) | 全通話、1 回 | N, P, T_in, T_out |
| 2 | 不備修正の差分再実行 | 不備 1 件ごと | k, s, T_in', T_out' |
| 3 | 語彙進化(検知・候補生成・検証) | 週次 | LLM は候補生成と検証のみ。検知は埋め込みで LLM 不要 |
| 4 | 品質ゲート(2 run 一致、合成データ回帰) | 月次 | r_judge |
| 5 | 合成データ生成 | 一度きり | 2,300 件 |

記号:

| 記号 | 意味 | 目安(第 1 段で実測) |
|---|---|---|
| N | 月の通話数 | 100,000 |
| P | 初回抽出のパス数(一段なら 1。構造 → 発話行為の二段なら 2 だが、2 パス目は入力を絞れる) | 1〜1.5 |
| T_in | 1 通話の入力トークン(日本語書き起こし + プロンプト固定部) | 4,000〜6,000 |
| T_out | 1 通話の出力トークン(構造 JSON + 根拠引用) | 500〜1,500 |
| k | 月あたりの不備修正回数 | 立上げ期 4〜8、安定期 1〜2 |
| s | 不備 1 件あたり、埋め直す通話の割合(構造層で絞る) | 5〜20% |
| T_in' | 埋め直し 1 件の入力(用件のターンのみ + 短いプロンプト) | T_in の 20〜40% |
| T_out' | 埋め直し 1 件の出力(新項目 1 つ + 根拠) | 50〜150 |
| r_judge | 2 run 一致を掛ける通話の割合(構造のみ、サンプル) | 5〜10% |
| θ | ローカル LLM の実効スループット(トークン/秒。入力の読込みと出力の生成で桁が違うので分けて測る) | 実測 |

## B2. 月あたりのトークン量

```
初回抽出      = N × P × (T_in + T_out)
差分再実行    = k × s × N × (T_in' + T_out')
2 run 一致    = r_judge × N × (T_in + T_out_judge)
語彙進化      = 候補数 × (数十件のサンプル × T_in) + 検証サンプル × T_in    ← 週次で数百万トークン程度。無視できる規模
```

目安値を入れると(N = 10 万、P = 1、T_in = 5,000、T_out = 1,000):

| 工程 | 入力トークン | 出力トークン | 初回抽出比 |
|---|---|---|---|
| 初回抽出 | 5.0 億 | 1.0 億 | 100% |
| 差分再実行(k = 4、s = 10%、T_in' = 1,500、T_out' = 100) | 0.6 億 | 0.04 億 | 約 11% |
| 差分再実行(安定期 k = 1) | 0.15 億 | 0.01 億 | 約 3% |
| 2 run 一致(r_judge = 10%、構造のみ出力 300) | 0.5 億 | 0.03 億 | 約 9% |

差分再実行は立上げ期でも初回抽出の 1 割強に収まる。s と T_in' の絞込みが効かない場合(全通話 × 全文で埋め直す)は k × 100% になり、月 4 回の不備修正で初回抽出の 4 倍を払う。**絞込みが原則 5 の成立条件である。**

## B3. 計算時間への換算

ローカル LLM では入力の読込み(prefill)と出力の生成(decode)で速度が桁違いに異なり、通常は出力の生成が支配的になる。月の計算時間は概ね次で見積もる。

```
時間(秒) ≈ 入力トークン / θ_in + 出力トークン / θ_out
```

夜間 8 時間 × 30 日 = 240 時間を枠とすると、初回抽出 + 差分 + 2 run の出力合計 約 1.1 億トークンを 240 時間で処理するには、θ_out ≈ 130 トークン/秒(バッチ処理での合計値)が要る。入力 6 億トークンは θ_in ≈ 700 トークン/秒が要る。これが候補モデルと実行系に求める最低ラインになる。24 時間連続稼働なら各 3 分の 1 で足りる。

θ は、モデルの大きさ、量子化、GPU、バッチ処理の実行系で大きく変わるので、本書では数値を置かない。採る場合は候補 2〜3 個を実際の環境で測る。

## B4. 設計で費用を抑えている点(すでに入っているもの)

| 抑制策 | 効く変数 | 出所 |
|---|---|---|
| 構造層で対象通話を絞ってから埋め直す(「苦情 × 更新案内」だけ読む) | s | 原則 5 |
| 用件のターン帰属を使い、用件レベルの項目は用件のターンだけを入力にする | T_in' | 原則 3(用件とターンの多対多) |
| 埋め直しは新項目だけを出力し、既存項目は再抽出しない | T_out' | 追加のみのスキーマ版 |
| 2 run 一致は構造のみ、サンプルのみ | r_judge | 原則 4 |
| 語彙進化の検知は埋め込みと件数で行い、LLM は候補生成と検証だけ | 工程 3 | [03_vocabulary.md](03_vocabulary.md) §2.1 |
| 根拠は位置参照を主にし、引用は逐語一致検証に必要な最短にする | T_out | [02_schema.md](02_schema.md) §3 |
| 判断列を保存せず導出する。判断の定義変更に再抽出が不要 | k | 原則 6 |

## B5. まだ入っていない抑制策(第 1 段の結果次第で採る)

| 抑制策 | 効く変数 | 条件 |
|---|---|---|
| 項目ごとのモデル分担。局面と用件帰属は良いモデル、発話行為は小型モデル | θ | 第 1 段で項目ごとの κ を測り、小型で足りる項目を決める |
| 不備修正を週次で束ね、複数の新項目を 1 パスで埋める | k | 運用 |
| プロンプト固定部の再利用(実行系の KV キャッシュ) | θ_in | 実行系の選定 |
| 安定した項目の蒸留。選択肢が安定し LLM ラベルが数万件たまった項目は小型分類器に置き換え、LLM は長尾のみ | 初回抽出の大半 | v1 以降。長尾での崩壊リスク([reference/feasibility_2026-09.md](reference/feasibility_2026-09.md) §3.5)があるため、構造には適用しない |
| 一部の列だけ外部 API に出す(マスキング後) | θ | ローカルで κ が足りない列がある場合 |

## B6. 廃止した方式との比較

問いのたびに原文へ定義文を当てる方式(廃止。決定記録 0003)は、1 回の問いに s × N × T_in を払う。差分再実行はこれに加えて過去分の埋め直しを 1 回払うが、以後は SQL だけで答える。同じ問い(または同じ項目を使う別の問い)が 2 回来た時点で差分再実行の方が安く、以後は差が開く。加えて、廃止した方式は問いを立てられる人が LLM を扱える人に限られる。

## B7. ローカルを採る場合の追加確認

ローカル LLM を動かす計算資源(GPU の有無、種類、枚数、メモリ)。未定なら候補の実行環境を借りて測るが、θ の実測値は環境に依存するので本番環境で再測定が要る。API 前提(決定記録 0006)のため当面は不要。
