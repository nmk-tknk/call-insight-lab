- 経緯は [history.md](history.md)、未決の論点は [open_issues.md](open_issues.md)。原則の唯一の置き場。

## 2. 原則(決定)

### 原則 1: 3 層の半構造化。項目は「通話で言われうることの役割」で固定し、問いから逆算しない

| # | 決定 | 根拠発言(依頼者) | 日付 |
|---|---|---|---|
| M1 | 通話は「原文(逐語)/ 構造 / 根拠(値と原文の対応)」の 3 層で保存する。キーワード検索(文脈が消える)と全文脈保持(集計のたびに全負担)の折衷が半構造化である。半構造化のスキーマを正しく定義できれば、後の論点は表現の揺れだけに落とし込める | 「キーワード検索だけだと文脈が消えるが、汎用的な集計の仕組みは簡単。文脈を完全に残そうとすると…限界あり。この折衷案が文章の半構造化だという認識。この半構造化のスキーマを正しく定義できれば、後の論点は表現の揺れだけに落とし込める」 | 2026-09-20 |
| M2 | 構造の項目は「通話で言われうることの役割」(誰が / 何をした / 何について / どの側面 / なぜ今 / なぜ / どうなった / どう感じた)で固定し、よく聞かれる問いから逆算しない。問いは項目の値の組合せで表す | 帰結 1〜4 の説明に「了解した。方向性はこれで良い」 | 2026-09-20 |
| M10 | 語彙に依存する構造化は汎用性を失う。構造化を問いや業種固有の語彙に依存させない | 「語彙依存にする構造化は汎用性なくなるでしょ」 | 2026-09-21 |
| M11 | 「語彙に該当がない」はスキーマの失敗であり、常態として容認しない。v0.4 はその認識で始めた | 「『語彙に該当がない』というのがまかり通っている前提がまず理解できない。それはスキーマの失敗だと捉えるべきという話でv0.4を作り始めた認識」 | 2026-09-22 |

「各項目の選択肢は育てる」とその手順(語彙進化ループ)は決定ではない(§4)。

### 原則 2: 集計は構造層の SQL だけ。原文へ LLM を当て直すのは不備を直すときだけ

| # | 決定 | 根拠発言(依頼者) | 日付 |
|---|---|---|---|
| M4 | 問いに答えるために原文へ LLM を当て直さない。原文に LLM を回し直すのは、スキーマの不備を直すときに限る | 「要はスキーマの不備を直すために、再実行することはあるということか？」→「了解した。方向性はこれで良い」 | 2026-09-20 |
| M5 | 集計は構造層に対する SQL だけで完結させる。LLM を扱えない人でも同じ数字が出ること(民主化)を目的とする | 帰結 1〜4 の説明への了解(M2 と同じ発言) | 2026-09-20 |
| M6 | 抽出は取込時に全通話・全項目に対して行う。問いが来てから読み直さない | 帰結 4 への了解(M2 と同じ発言) | 2026-09-20 |

分析列を閉じた語彙に限る規約、`other` / `unknown` の扱いは案([02_schema.md](02_schema.md) §11)。

### 原則 3: 分析単位は「用件」、原子単位は「ターン」、通話は導出

決定は M7 の「構造 = 局面、用件の切り出し、ターン帰属」のみ。局面と用件の直交構造、非連続な帰属、通話行の導出は案([02_schema.md](02_schema.md) §10)。用件の定義と粒度は [04_analysis_needs.md](04_analysis_needs.md) §0.5(案)。

### 原則 4: 品質は「証明」ではなく「担保」する。人手ラベルなしで

決定は R2(人手ラベリングはほぼ不可能)のみ。担保の方法(逐語一致、2 run 一致、分割半分再現、合成データ回帰、根拠 30 件目視、レシピの省略不可)は案([05_poc_plan.md](05_poc_plan.md) §3)。

### 原則 5: 構造で覆えない問いは、スキーマの不備として塞ぐ

| # | 決定 | 根拠発言(依頼者) | 日付 |
|---|---|---|---|
| M3 | 構造層だけで答えられない問いは「答えられない問い」ではなく「スキーマの不備」として塞ぐ。到達目標は目録の問いのすべてであり「N 件中 M 件」ではない | 「覆えない問いがあることはスキーマの不備だと捉えるべきです」、帰結 3 に「了解した」 | 2026-09-20 |

不備を「選択肢が足りない」と「項目がない」に分け、前者を `other` の埋め直しで処理する運用は、帰結の説明に含まれ方向性の了解を得たが、2026-09-22 に依頼者が前提自体に疑義を示した(M11、[history.md](history.md))。扱いは未決([open_issues.md](open_issues.md) S17)。

### 原則 6: 注釈は「構造」と「明言」だけ。判断は集計時の規則で導く(v0.4)

| # | 決定 | 根拠発言(依頼者) | 日付 |
|---|---|---|---|
| M7 | 事実関係が明確な部分と主観が混じる部分を分離する。注釈(LLM が書くもの)は構造(局面、用件の切り出し、ターン帰属)と明言(誰が何を言葉にしたか。引用付き)だけとし、混乱・動機・結果・受容・横断フラグ・感情は保存せず、集計時の規則(SQL のビュー)で導く。明言されていない含意は「不明」と数える | 「事実関係が明確な部分と主観が混じる部分を分離すべきでは？」「事実のみを構造化し、推論は集計時の工夫でカバーできませんか？」「了解した。もともと依頼されていた事項を完結させて、v0.4にしましょう」 | 2026-09-20 |
| M8 | 感情は推定になるので、表出(言葉にしたもの)のみを事実として扱い、口調からの推定はしない | 「感情はどうしてもすいていになりますよね」→ 表出のみとする案に「了解した」 | 2026-09-20 |
| M9 | v0.3 / v0.3.1 のスキーマは依頼者が内容を理解していないものとして扱い、v0.4 を正とする | 「v0.3やv0.3.1の内容はllmが勝手に作ったもので私は内容を理解していません」 | 2026-09-20 |

v0.4 の理由と例外(構造は注釈層に残す)は案([02_schema.md](02_schema.md) §1)。発話行為を問いの有無によらず全種類抽出することは M10 からの帰結として提示中([open_issues.md](open_issues.md) A7)。

## 3. 目録とテーマ(決定)

| # | 決定 | 根拠発言(依頼者) | 日付 |

| C1 | 分析ニーズの目録の役割は、「特定のテーマを拾えるか」という曖昧な問いの解像度を上げること。「用件が解決したか」「未解決の内訳が〇〇か」も特定のテーマである | 「特定テーマを拾えるかどうかが全てに思える。用件のが解決したかや未解決の内訳が〇〇かなども特定のテーマと言える。特定のテーマを拾えるかという曖昧な問を解像度上げるために我々はこの目録を作っているのではないか？」 | 2026-09-21 |

| C4 | 問い 23 はターン数ではなく時間で測る | 「ターン数は意味がないので、測定しない。まだ時間の方が良い」 | 2026-09-21 |
| C5 | 未解決の理由(代理店でしか受け付けられない、など)をスコープに含める(問い 45) | 「#22 未解決の理由(代理店でしか受け付けられない。)もスコープとしたい」 | 2026-09-21 |
