## 2. 結論

**作る価値はある。作るものは「汎用の分析器」ではなく「同じ定義・同じ手順・同じ根拠で数字が出る基盤」である。**

- 通話を LLM で構造化し、その上を単純集計で分析するアプローチは成立する。研究・商用製品の双方がこの方向に収斂している([reference/feasibility_2026-09.md](reference/feasibility_2026-09.md))。
- 課題の本質が「分析品質」であるなら、LLM を自由に使わせる限り解決しない。的外れな分析の原因の大半は、抽出ミスではなく分析手順の欠陥(比較対象がない、分母がない、都合のよい引用だけ見る、定義が人によって違う)にある。これは「同じ定義のデータ」と「決まった手順」を通さないと防げない。汎用ツールの価値はここにあり、抽出そのものはコモディティである。
- 現状の課題「LLM で誰でもそれっぽい分析が出せてしまい、歪んだ結果を信じ込む」に対する解は、抽出精度の向上ではなく、**定義・手順・根拠の強制**にある。

**作るべきでないもの**

- 50 列級の網羅的スキーマ(精度が崩れ、誰も定義を追えない)
- 「何でも聞ける」自然言語インターフェースを主機能にすること(再現性のない結果を量産し、現状の課題を再生産する)
- 人手ラベル前提の精度保証機構(回らない)

## 3. 分析目的の分解

### 3.1 目的 (a): 特定テーマの入電増加の真因調査

分析者が実際にやるべき手順を書き下すと次のようになる。

1. テーマを定義する(構造層の項目の条件式。[04_analysis_needs.md](04_analysis_needs.md) §0.5)。
2. 該当件数の時系列を出し、急増期間と比較用の平常期間を決める。**分母(総入電数)で正規化する。**
3. 急増期間と平常期間で、該当通話のファセット分布を比較する。用件、きっかけ、対象、混乱の対象、結果など。差が大きい順に並べ、効果量と信頼区間を出す。
4. 差が大きい軸について、**両期間から無作為抽出した根拠引用を並べて読む。** ここで仮説が立つ(「9 月の改定通知の文面 X が誤解を生んでいる」等)。
5. 仮説を検証する。仮説を新しいテーマ(条件式)として集計し、時系列が急増と一致するか、急増期間に集中しているかを確認する。
6. 反証を探す。仮説に該当しない急増分がどれだけ残るかを示す。

「誰でもそれっぽい分析」は、この手順の 2(分母)、3(比較対象)、6(反証)を飛ばして 4(引用)だけをやることで生まれる。ツールはこの手順を**飛ばせない形**で提供する。

### 3.2 目的 (b): 「わかりづらい」と訴えるパターンの特定

「わかりづらい」は特定テーマではなく、あらゆる用件に横断する**信号**である。したがって全通話に対して常時抽出する。訴え方は、直接(「わかりにくい」と明言)/ 間接・誤解(誤解した状態で入電)/ 間接・確認(既に案内済みの内容を確認するための入電)に分かれる。分析は「混乱ありの用件を混乱の対象で集め、件数・推移・下流コスト(再入電、未解決、否定的な表出)で順位付けし、各群の根拠引用を読む」で完結する。間接の検出こそが LLM を使う意味であり、キーワード検索では拾えない部分である。同時に、間接は LLM が最も過検出しやすい部分でもあるため、品質ゲートの検証対象の筆頭になる。v0.4 では間接の誤解を「顧客の主張にオペレータの訂正が続く、または主張が既知の誤解一覧にある」という規則で導く([02_schema.md](02_schema.md) §4)。

### 3.3 (a)(b) は代表例にすぎない

2 つの目的はどちらも、少数の汎用ファセットから組み立てられる。「入電増の真因」は「テーマ該当通話の時系列」+「急増期間と平常期間のファセット分布の差分」、「わかりづらい」は横断的なファセット(混乱とその対象)である。目的固有のものは薄く、共通基盤は厚い。社内から来る多様な問いを構造層で表現できるかは、[04_analysis_needs.md](04_analysis_needs.md) の目録で確かめる。

## 4. 原則

### 原則 1: 項目(スロット)は「通話で言われうることの役割」で固定し、選択肢は育てる

通話の構造化は、キーワード検索(文脈を失うが集計は簡単)と全文脈保持(集計のたびに全負担)の折衷である。**原文**(発言を逐語で残す)、**構造**(用件ごとに決まった項目へ決まった選択肢から値を入れる)、**根拠**(各値が原文のどこから決まったか)の 3 層を持ち、集計は構造層に対する SQL だけで完結させる。

構造層の項目は「よく聞かれる問い」から逆算しない。問いから作ると問いが増えるたびに項目が足りなくなる。代わりに、顧客の発言を**役割**に分解し、その役割の一覧を項目にする。誰が / 何をした / 何について / その何のどの側面が問題か / なぜ今 / なぜ / どうなった / どう感じた。問いは項目の値の組合せで表せるので、新しい問いは新しいタグではなく新しい組合せになる。**項目は固定し、各項目の選択肢は育てる。** 選択肢を育てる手順(検知 → 候補生成 → 自動検証 → 暫定採用 → 安定化 → 履歴整合)は固定し、人は承認者ではなく拒否権者とする([03_vocabulary.md](03_vocabulary.md))。

### 原則 2: 分析列は閉じた語彙のみ。原文を読み直すのは構造を直すときだけ

分析に使う列はすべて列挙・コード・真偽値。自由記述は (a) 語彙を育てる材料(要約、`other_text`)と (b) 検証用の根拠(逐語引用+位置参照)の 2 用途に限定し、レポートの軸には使わない。すべての列挙列に `other` と `unknown` を持ち、`other` 率を語彙見直しのトリガにする。

**問いに答えるために原文へ LLM を当て直すことはしない。** それをすると LLM を扱える人しか問いを立てられず、民主化の外に出る。原文へ定義文を当てるのは、構造を直すときの 2 場面に限る。(1) 足りない選択肢や項目が実際に件数を持つかを確かめるとき、(2) 足したあとに過去分を埋め直すとき。各選択肢は包含・除外基準の定義文を持ち、その定義文がそのまま埋め直しの指示になる。

### 原則 3: 分析単位は「用件」、原子単位は「ターン」、通話は導出

通話は「あいさつ → 目的発話 → 本人確認 → 議論 → クロージング」という**局面**と、その上を非連続にまたがる**用件**という、直交する 2 つの構造を持つ。通話 1 件 = 1 行ではこの構造が消え、連続区間で切ると 2 つの構造を混同する。

- **ターン**が原子単位。各ターンに局面ラベルと 0〜複数の用件 ID を付ける(ISO 24617-2 の多次元注釈、AMI の機能的/内容的トピックの分離に相当)。
- **用件**が集計単位。用件は目的発話と議論をまたぎ、本人確認や保留で中断されても同じ ID で復帰する(Grosz & Sidner の焦点スタック)。用件の定義と粒度は [04_analysis_needs.md](04_analysis_needs.md) §0.5。
- **通話行**は用件と局面から導出する(用件数、主用件、全用件解決、局面ごとの所要、冒頭/末尾の感情表出)。
- 保留・転送は局面ではなくイベント。

これにより、通話単位では原理的に見えなかった「2 件目以降の用件の内訳」「述べられたが議論されなかった用件(取りこぼし)」「本人確認に費やす割合」が数えられる。

### 原則 4: 品質は「証明」ではなく「担保」する。人手ラベルなしで

絶対精度は証明できないが、次を機械的または数分の作業で担保する。

| 検証 | 防ぐもの |
|---|---|
| 根拠の逐語一致・位置整合 | 幻覚・捏造 |
| 全ターンの局面付与、用件 ID の参照整合、本人確認ターンに用件なし | 帰属の構造ミス |
| 2 モデル間(または言い換えプロンプト間)一致 | プロンプト依存の不安定な判定 |
| 分割半分再現 | ノイズを傾向と誤認 |
| 合成データ回帰 | 抽出器・モデル更新時の劣化 |
| CRM 事実との整合(未解決 → 再入電) | 系統的誤検出 |
| 既知事例の盲検再現 | 分析手順そのものの妥当性 |
| 分析者による根拠 30 件目視 | テーマ定義の過検出。未通過は「未確認」表示 |

加えて、**分析手順(レシピ)が分母・比較期間・両側からの無作為引用・未説明残余を省略できない**形で提供される。結論を書くのは人。ここが「信じ込み」への最も直接的な対策になる。詳細は [05_poc_plan.md](05_poc_plan.md) §3。

### 原則 5: 構造で覆えない問いは、スキーマの不備として塞ぐ

社内から来る問いのうち構造層だけで答えられないものは、「答えられない問い」ではなく「直すべき不備」として起票する。不備は 2 種類に分かれ、対処が決まっている。

| 不備 | 例 | 対処 |
|---|---|---|
| 選択肢が足りない(項目はある) | 解約理由に「補償内容への不安」がない | 原則 1 の手順で自動追加し、`other` だった通話だけ埋め直す |
| 項目がない(役割が抜けている) | 「対象のどの側面が問題か」がない | 追加のみの新版を出し、関係しうる通話だけ埋め直す |

埋め直しは差分で行い、既存の項目・集計は変えない。埋め直した結果は別の実行として保存し、どの定義・どのモデルで埋めたかを追えるようにする。到達度の目標は「目録の問いのすべて」であり、「N 件中 M 件」ではない。測るのは「不備を見つけてから塞ぐまでの時間」と、埋め直しの計算負荷である。

### 原則 6: 注釈は「構造」と「明言」だけ。判断は集計時の規則で導く(v0.4)

LLM が注釈層に書くのは、構造(局面、用件の切り出し、ターン帰属)と発話行為(誰が何を明言したか。引用付き)だけとする。混乱の型・動機・結果・受容・横断フラグ・感情は保存せず、発話行為と業務知識表(既知の誤解一覧)から SQL のビューで導く。明言されていない含意は「不明」として数え、推し量らない。感情は表出のみを事実とし、口調からの推定はしない。内面の推定が要る場合は「推定」と名の付く別の実行に隔離する。

理由は 3 つ。(1) **再現性**: 「なぜこの通話が誤解と数えられたか」が、LLM の判断ではなく「主張 A にオペレータの訂正 B が続いた」という規則で説明できる。(2) **変更の安さ**: 判断の定義は必ず揺れる。ビューに置けば、定義を直すのは SQL の修正で済み、10 万件を LLM に回し直す必要がない。(3) **抽出の易しさ**: 明言の記録は引用の逐語一致で全件を機械検証でき、小型モデルの守備範囲が広がる。2 run 一致が要るのは構造だけになる。

例外は構造(用件の切り出し、帰属、局面の境界)である。これは明言ではなく対話構造の解釈で、集計時には導けない。主観の度合いは低く、参照整合と 2 run 一致で機械的に検証できるので、注釈層に残す。失うのは明言されていない含意だけで、どれだけ失うかは PoC 第 1 段で「推論あり抽出」と比較して測る([05_poc_plan.md](05_poc_plan.md) §5)。

発話行為の種類は業種によらない役割の一覧であり、目録の問いの採否にかかわらず常に全種類を抽出する(決定記録 0009、承認待ち)。

## 5. 全体像(処理の流れ)

1. **取込**: 書き起こしをマスキングし(ローカル)、原文層に保存する。マスキングの位置と種別を残す。
2. **基盤抽出(全件・バッチ)**: 第 1 段でターンごとの局面と用件 ID の帰属、第 2 段で用件ごとに「目的発話+その用件のターン」だけを入力して発話行為を抽出する。入力が絞られるので判定が安定し、本人確認ターンを LLM に渡さずに済む。
3. **機械検証**: 原則 4 の構造チェックと逐語一致。不合格行は集計から除外または要確認。
4. **導出**: 発話行為と業務知識表から、混乱・動機・結果・受容・横断フラグ・感情を SQL のビューで導く。
5. **語彙進化(週次)**: `other` 率の管理図、要約埋め込みの増分クラスタリング、既存タグの分裂・不安定化を検知 → LLM が候補(名前・定義・包含/除外基準・階層位置)を生成 → 自動検証 → 暫定採用と差分バックフィル → 安定化で昇格。人は週次ダイジェストに拒否・改名・統合を指示できる。
6. **分析レシピ**: 「急増真因」(時系列 → 期間比較 → 差分順位 → 引用対比 → 仮説再集計 → 反証)と「わかりづらいパターン」(混乱 × 対象 × 下流コスト)。省略不可の工程を持つ。

## 6. 汎用性の見立て

- **汎用にできる部分(厚い)**: 構造化抽出、語彙進化、品質ゲート、期間比較の統計。これらは目的が変わっても再利用される。
- **目的ごとに作る部分(薄い)**: 分析レシピ。ただしレシピは「比較軸を選び、順に表示する」程度の薄さで、1 本あたり数日で追加できる。
- **汎用にしてはいけない部分**: 結論を出す工程。ここを LLM に委ねると現状の課題に戻る。

「様々な分析目的に汎用で使えるものを作る」は、**「汎用の答えを出す装置」なら筋が悪く、「汎用の証拠と手順を用意し、答えは人が出す装置」なら筋が良い**。汎用性の測り方は、[04_analysis_needs.md](04_analysis_needs.md) §0.1(表現できるか / 値があるか / 信頼できるか)による。

## 7. できること・できないこと

| できる | できない(別の単位・手段が要る) |
|---|---|
| 用件数ベースの件数・割合・推移・セグメント比較 | 応対品質のコーチング(発話行動の別スキーマ) |
| 急増の真因候補をタグの組み合わせの差として提示 | 語彙にない真因の即時命名(暫定タグで数週間の遅れ) |
| 「わかりづらい」対象と訴え方の特定 | 言い方・温度感の解釈(口調からの感情推定) |
| 述べられたが議論されなかった用件の検出 | 顧客ジャーニー(顧客単位テーブルと顧客 ID が要る) |
| 本人確認・保留の所要と位置(ターン時刻がある場合) | 施策効果の因果的検証(実験設計が要る) |
| 解決状況と再入電の自己申告の整合 | 解約予測(目的変数との結合と学習が要る) |

「この基盤で答えられない問い」の一覧をツールの仕様の一部にする。範囲外の問いは人の読解に回すと決めておくことが、範囲を広げることと同じくらい重要。

## 8. 先例との関係

構造の各要素には直接の先例がある([reference/prior_art.md](reference/prior_art.md))。ISO 24617-2 の多次元・不連続な注釈単位、AMI の機能的/内容的トピック分離と根拠リンク、Grosz & Sidner の焦点スタック、IBM 2007 / NTT 2018 の通話局面分類、DECODA の不連続テーマ、Oracle 2025 の concern、商用要約の issue / outcome / action item 三点セット、AWS / Google の位置参照付き根拠。独自部分(ターンと多対多で結びつく用件エンティティ、明言のみの注釈と導出規則)も CRM の親子ケースや対話行為の注釈に先例がある。
